# Agentic development lifecycle

**Skills describe methods. Agents own responsibilities. The host supplies execution and
tools.** They are not three names for the same object. One running agent can use several
skills. A saved agent definition does not start a process, and a skill does not grant access.

This map places all **49 canonical skills and 32 agents** in the lifecycle. Placement means
"useful here", not automatic execution, a required agent for every step, or runtime certification.
The metadata and source definitions remain under `.developer/`.

## Stage gates and handoffs

| Stage | Entry and work | Output required before the next stage |
| --- | --- | --- |
| 0. Prepare | Select source, host, account, repository and permission ceiling | Verified prerequisites, exact working folder/branch and bounded authorization |
| 1. Understand | Read approved requirements; resolve material ambiguity | Testable scope, acceptance criteria and explicit human decisions |
| 2. Design | Inspect code and constraints; compare implementation choices | Source-grounded design, interfaces, risks and approved material choices |
| 3. Plan | Split work by real dependencies and ownership | File-level plan, tests, integration owner and approved implementation scope |
| 4. Build | Observe the intended failing test; implement and refactor | Candidate revision, observed RED/GREEN evidence and bounded changes |
| 5. Verify | Run the target repository's checks against the exact candidate | Fresh results; PASS, FAIL, BLOCKED, SKIPPED and stale evidence kept distinct |
| 6. Review | Review the actual diff; assess findings against requirements | Supported findings, explicit decisions and independent repair acceptance when needed |
| 7. Diagnose and repair | Reproduce an observed failure; test causal hypotheses | Bounded repair and regression evidence; return to verification and review |
| 8. Release handoff | Check release requirements and unresolved risk | Human-owned merge/deployment decision; publication requires its own authorization |
| 9. Learn and measure | Use approved delivery, usage and outcome evidence | Source-linked knowledge, validated measurements and proposed follow-up work |

This is a loop, not a waterfall. A failing build goes to diagnosis. A design question returns
to clarification. A changed requirement updates its tests. A blocked prerequisite stops
the affected branch rather than producing a success-shaped fallback.

`run-tests` and the other Playwright-specific methods do not replace a repository's
Vitest, unit-test or CI policies. `verify-change` checks the evidence from the appropriate
runner; it is not another test runner. Accessibility review and verification remain
distinct from authoring and fixing; a clean automated scan is not full accessibility proof.

These are role definitions, not proof that the host has launched them. A stage can be
completed by one authorized agent without constructing a squad.

The new evidence and coordination roles are read-only. Their output is a proposal,
evidence package or handoff, not a write, deployment, message or automatic agent launch.
Existing leads and critics retain their own tool and approval contracts.

## One agent, specialists, or a squad?

| Arrangement | Choose it when | Relationship and boundary |
| --- | --- | --- |
| One agent | The work is one continuous trace with a small context | One owner selects relevant skills and returns evidence; no delegation needed |
| Main agent with a specialist | One bounded question needs separate expertise | Main owner sends the exact candidate/question, receives findings and integrates them |
| Squad | Multiple tasks genuinely need independent contexts and are authorized | Coordinator owns a dependency graph; workers own non-conflicting scopes; integration is explicit |
| Independent validator | Repair acceptance must be separate from implementation | Validator checks the original failure and regressions; it does not author the repair |

A squad is not a fourth artifact type in this library. It is an execution arrangement
provided by a compatible host. `coordinate-work` proposes ownership and dependencies;
it does not create sessions or install an orchestrator. Parallelism is optional.

## Context and source boundaries

Personal versus work is a **data/account boundary**, not a different set of generic
engineering methods. Apply the same skills to either context, but select approved
repositories, configuration, memory and credentials separately. A folder, worktree or
session label is not a security sandbox.

Provider adapters live outside the generic library. An adapter can normalize an approved
record for a canonical skill or prepare a role handoff. It does not duplicate the generic
method, inherit permission from another account, or automatically invoke the next role.

When another plugin offers a similarly named skill, choose an effective source and
qualified ID explicitly. Do not mix independent accessibility review implementations
silently, and do not count installed copies as additional unique capabilities.

## A small worked route

For a bounded defect: prepare the repository and evidence; reproduce with `analyze-bug`
and `root-cause`; use `fix-bug` for an authorized repair; check fresh results with
`verify-change`; obtain independent `repair-validator` acceptance and relevant
`code-review`; then give the human the release handoff. Use the repository's required
runner throughout. A validator's rejection returns to diagnosis, not straight to merge.

Start with one task and one owner. Add a specialist only for a bounded independent
question. See [architecture](/architecture), [skills](/skills) and [agents](/agents).
